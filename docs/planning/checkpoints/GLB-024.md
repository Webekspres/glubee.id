# Checkpoint GLB-024: Penghapusan akun dengan masa jeda 3 hari

Task: [GLB-024](https://app.clickup.com/t/86eyvady6) · Jadwal 6-7 Oktober 2026 (dimulai lebih awal 1 Oktober) · Kebutuhan: FR-DELETE-001, FR-DELETE-002, BR-RULE-009 s.d. 012, LEGAL_OPERATIONS §6

## Acceptance criteria (ClickUp)

1. Pengajuan menghentikan aktivitas/job; mode terbatas hanya ekspor, batal, dan keluar; admin diberi tahu tanpa hak veto.
2. `scheduled_for = requested_at + 3 hari`; konfirmasi menampilkan tanggal/jam lokal dan UTC.
3. Pembatalan oleh pengguna tidak mengirim ulang job lama; eksekusi setelah tenggat idempotent, membersihkan data, dan membuat tombstone; kegagalan terpantau.

## Temuan analisis

- Sudah ada: tabel `deletion_requests` (state `pending/cancelled/executing/completed/failed`, satu permintaan aktif per pengguna, constraint 3 hari), `deletion_tombstones`, status profil `deletion_pending`, RLS yang menutup data kesehatan saat `deletion_pending`, ekspor yang tetap jalan saat jeda (GLB-023), halaman Status akun.
- **Penghalang**: `deletion_requests.user_id` memakai `ON DELETE RESTRICT` ke `auth.users`, sehingga akun tidak bisa dihapus. Perlu diubah ke `ON DELETE SET NULL` (kolom boleh kosong) agar catatan permintaan tetap ada sebagai bukti tanpa identitas.
- Semua tabel data pengguna lain sudah `ON DELETE CASCADE` ke `auth.users`; log admin `SET NULL`. Menghapus baris `auth.users` menghapus seluruh data aktif sekaligus (termasuk sesi dan token GoTrue).
- `pg_cron` sudah dimuat di image `supabase/postgres:17.6.1.136` (lokal dan production) dan bisa dibuat oleh role `postgres` (diuji lokal). Eksekusi terjadwal tidak perlu crontab VPS atau workflow baru.
- SMTP Brevo sudah tersedia di container app (`SMTP_*`), modul `sendEmail` ada tetapi belum dipakai aplikasi.
- Pembatalan tidak boleh mengaktifkan kembali akun yang sebelumnya dinonaktifkan admin, jadi status sebelum permintaan disimpan.

- **Penghalang kedua (ditemukan saat tes)**: tabel append-only (`consent_receipts`, `contact_consents`, `notification_attempts`, `glucose_entries`, `cookie_consent_receipts`) menolak DELETE/UPDATE lewat trigger, sehingga cascade penghapusan akun selalu gagal (SQLSTATE 55000) untuk akun yang punya bukti persetujuan, yaitu semua akun. Diselesaikan dengan penanda transaksi `glubee.account_deletion` yang hanya dinyalakan `execute_due_deletions()`; di luar itu tabel tetap append-only (diuji).
- Bukti persetujuan ikut terhapus bersama akun (minimisasi data). Bukti cookie dipertahankan tanpa identitas (FK `SET NULL`). **Perlu konfirmasi legal** apakah bukti persetujuan harus disimpan lebih lama setelah akun dihapus.

## Keputusan desain

| Topik | Keputusan |
|---|---|
| Pengajuan | `POST /api/account/deletion` dengan re-auth (sama dengan ekspor: password, atau login Google ≤10 menit) + centang "Saya mengerti". RPC `request_account_deletion()` mengubah status ke `deletion_pending`, menyimpan status sebelumnya, membuat permintaan `scheduled_for = now() + 3 hari`, dan membatalkan semua job notifikasi yang masih antre. |
| Siapa boleh mengajukan | Akun `active`, `onboarding`, atau `suspended` (hak penghapusan UU PDP). |
| Pembatalan | `DELETE /api/account/deletion` dengan re-auth, hanya sebelum tenggat. Status kembali ke status sebelumnya (suspended tetap suspended; lainnya dihitung ulang). Job lama tetap `cancelled`, tidak dikirim ulang. |
| Eksekusi | `private.execute_due_deletions()` via `pg_cron` setiap 15 menit, maksimal 50 akun per jalan. Per akun: tandai `executing`, simpan tombstone `sha256(user_id)` dengan `backup_expiry_after = now() + 8 hari` (backup harian disimpan 7 versi), hapus `auth.users` (cascade), tandai `completed`. Gagal: state `failed` + kode error tanpa data pribadi, dicoba ulang di jalan berikutnya. Idempoten: hanya memproses `pending/failed` yang sudah lewat tenggat. |
| Pemberitahuan admin | Bagian "Permintaan penghapusan" di `/admin-xyz` (email, jadwal, status, termasuk yang gagal). Tanpa tombol tunda/batal. |
| Email ke pengguna | Konfirmasi saat mengajukan (jadwal lokal + UTC, cara membatalkan) dan saat membatalkan. Best-effort: kegagalan email tidak membatalkan permintaan. |
| Tampilan | Profil: bagian "Hapus akun" (gaya bahaya) + dialog. Status akun saat jeda: jadwal penghapusan (lokal dan UTC), unduh data, batalkan, keluar. |

## Dampak ke aplikasi

- **Database**: migration baru (ubah FK `deletion_requests`, kolom status sebelumnya dan kode error, 4 fungsi, jadwal `pg_cron`). Production: migration dijalankan manual di VPS seperti sebelumnya. **Setelah migration ini, akun yang mengajukan penghapusan benar-benar hilang 3 hari kemudian**, termasuk akun demo bila ada yang menekan tombolnya.
- **Backup**: tombstone dipakai saat restore agar akun terhapus tidak hidup kembali (runbook restore perlu langkah rekonsiliasi; terkait GLB-028).
- **API**: `POST`/`DELETE /api/account/deletion`; helper re-auth dipakai bersama ekspor.
- **UI**: Profil, Status akun, Admin.
- **Email**: pertama kali aplikasi (bukan GoTrue) mengirim email lewat Brevo; kuota Free 300/hari.
- **Tes**: pgTAP (pengajuan, pembatalan, status suspended dipertahankan, eksekusi menghapus data dan membuat tombstone, idempoten, gagal tercatat), unit (format jadwal lokal/UTC), Playwright (ajukan, mode terbatas, ekspor tetap bisa, batal, admin melihat permintaan).
